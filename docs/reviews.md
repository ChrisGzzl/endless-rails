# Endless Rails 代码与文档评审记录

记录对 `endless-rails/` 的架构评审结论，供后续改动参考。

评审基线：`main` @ `a29c4fb`（2026-09-27）。测试状态：24 个测试文件全部通过。

一条通用前提：本项目的测试全部经由 `test-harness.cjs` 把脚本喂进 `vm` 沙箱执行，**断言的是行为，不是渲染**。因此下面标为"已测"的项，指的是逻辑被覆盖，不代表真实浏览器/移动端表现已验证。

## 一、已确认问题

### 1. 版本查询参数未统一，旧 CSS 缓存不会被击穿

严重度：高。这是本轮唯一会直接造成线上故障的问题。

`worklog.md` 第 52 行声称"关键脚本/样式缓存版本统一为 `20260922-v090a2`"，但 `index.html` 里实际是十代互不相同的值：

| 资源 | 版本参数 |
| --- | --- |
| `styles.css` | `20260923-battle2` |
| `ui-wasteland.css` | `20260923-v090rc4` |
| `home.css` | `20260923-ui1` |
| `ui-refresh.css` | `20260923-ui1` |
| `battle-ui.css` | `20260923-battle3` |
| `edge-ui.css` | `20260923-edge2` |
| `sand-ui.css` | `20260924-sand3` |
| `icon-ui.css` | `20260923-icons1` |
| `reference-ui.css` | `20260927-mobile8` |
| `mobile-icons.css` | `20260927-mobile8` |
| `manifest.webmanifest` (start_url) | `20260922-v090a2` |
| 14 个脚本标签 | `20260923-v090rc4` |

风险点具体在于：`sand-ui.css` 停在 `20260924`，而 `reference-ui.css` 在 `20260927`。09-27 那轮"整套手机界面"改动同时修改了两个文件（见 `c21fb4b` diff，`reference-ui.css` +386 行），但只有 `reference-ui.css` 的参数被推到了 `mobile8`。**`sand-ui.css` 的旧缓存不会被击穿**，用户拿到的会是新旧混合的样式。

同类问题 rc.2 上线复核时已经踩过一次，worklog 第 94 行的记录是"浏览器复用了旧 iframe HTML"，随后"为测试入口和诊断脚本增加版本查询参数"。那次是漏加，这次是各加各的——手动维护 18 个独立版本号，漏一个不会有任何提示。

建议：要么统一成单个 `RELEASE` 常量并在构建/发布脚本里一次性替换，要么改用内容哈希。继续手写只会重复踩。

### 2. `game.js` 里 8 处降级桩会让加载失败静默带错数值运行

严重度：中高。改动小，收益明确。

`game.js` 开头对每个依赖模块都配了内联 fallback，例如：

```js
const balance=window.EndlessRailsBalance||{START_TRAIN_LENGTH:3, ...};
```

共 8 处。后果是：脚本加载失败或顺序错误时，游戏不报错，而是带着**另一套手抄的数值**继续跑。而这些数值确实和真值不同——真 `balance.js` 与桩里的 `ENEMY_CAP`、`SPAWN_INTERVAL_*`、`initialWaveCount` 三处对不上，平衡数值被维护了两份，其中一份只在故障时生效。

这正是 alpha.3 那次事故的机制：`longterm.js` 整段未执行，游戏"回退到空 Meta 实现"（worklog 第 60 行），线上表现是点"远征准备"直接跳过界面。当时能快速定位是因为报的是 `SyntaxError`；如果换成一次静默的 `||` 兜底，同样的失败会表现成"数值不对"而不是"崩了"，定位成本高一个量级。

建议：桩换成 `throw new Error("balance.js 未加载")`，测试里按需注入最小替身。失败要响。

### 3. `updateHud()` 是无变更检测的每帧全量 DOM 写入

严重度：中。

`game.js:741` 是一个 1728 字符的单行，一次写入二十多个 DOM 节点，并且每帧重算两次百分比字符串。它同时混用两套取元素风格：全文件 `$("id")` 出现 30 次、`ui.*` 出现 49 次。

注：rc.1 已经做过一轮性能处理（worklog 第 70 行："HUD 常规刷新限制为 10Hz"），所以当前不是热点。但**没有变更检测**这一点没被处理——10Hz 下每帧仍无条件重写全部节点。随着 HUD 继续增长（09-23 到 09-27 四轮 UI 改动都在动这块），这会变成低端机上的帧预算问题。

建议：加脏值比较，或至少用 `requestAnimationFrame` 合并同一帧内的多次调用。

### 4. 全局作用域仅剩一处真实重名

严重度：低（当前不触发），但值得记录成因。

`state` 在两个文件里被声明：`game.js:38`（god object）与 `qa.js:6`（`const state=()=>...`）。

当前不炸，是因为 `qa.html` 用 iframe 把游戏隔离在另一个文档里，两个 `state` 分处不同 realm。这是**结构上的巧合而非设计**：`qa.js` 本身在同一页面里也确实声明了 `state`，任何人把 `qa.js` 移进主文档就会立刻白屏。

另注：`STORAGE_KEY` 曾在 `longterm.js` 与 `run-record.js` 重复声明并导致 alpha.3 阻断（worklog 第 60 行）。该问题**已修复**，`longterm.js:2` 现在是 IIFE 包裹的。

建议：`qa.js` 的 `state` 改名（如 `readState`）。

### 5. 加载顺序是隐式契约，只有测试在守

严重度：低，但会随文件数增长。

`test-harness.cjs:71` 用 `assert.deepEqual(scriptNames, [...18 个名字按序])` 钉死了加载顺序。思路对，但运行时本身对此零防护——调整 `index.html` 里的 script 顺序不会有任何提示，只会某个功能安静地失效（配合问题 2 的桩，甚至不静默失效而是带错值运行）。

建议：10 个纯模块（`balance` / `progression` / `combat-effects` / `control` / `route-events` / `run-record` / `motion` / `longterm`，以及 `cloud-sync`）已经是干净的 UMD 式写法，改成 ESM 只差 `import`/`export`。浏览器原生支持，不需要打包器，加载顺序问题会永久消失。

### 6. 单行压缩风格

严重度：低，但影响协作。

`game.js` 有 24 行超过 400 字符，最长一行 1728 字符（即 `updateHud`）。`renderer.js` / `armory.js` 无此问题，`meta-ui.js` 有 3 行。

这个风格使得：diff 无法定位到具体改动、评审只能整行看、冲突解决靠人工判读。建议新代码避免，存量可在拆分时顺带处理。

## 三、worklog 相关

### 3.1 覆盖情况（已核对，无缺口）

初判认为 09-27 之后的五个提交未记录，**该判断错误**。逐个核对结果：

| 提交 | worklog 对应条目 |
| --- | --- |

| `132e1bc` | 第 217 行"列车页、图标与底栏修正" |

`a6eba95` 是 2026-09-10 的提交，worklog 第 19-21 行已记录。

唯一的实质差异是：上述五个提交**都没有在 worklog 里写明提交哈希**（只有 `c21fb4b`、`772a783`、`f8e5872` 等少数几个被引用）。worklog 与 git 历史目前靠内容对应，而非哈希对应。

### 3.2 条目排序混用了日期与逻辑

09-23 的条目被 09-24 的条目（第 169 行）隔开，形成：`rc.3` → `rc.4` → 六张概念图 → 战斗 HUD → 战斗可读性 → **09-24 色板** → **回到 09-23 ImageGen 图标** → 09-26 → 09-27。

按内容逻辑，第 180 行的 ImageGen 图标那条应排在第 169 行的色板条**之前**——因为色板条自己说"选用了沙色纸面色板"是在**已有图标**基础上调配色。现在两处排序互相矛盾。

### 3.3 缺少"当前状态"入口，且文档持续增长

worklog 是 39KB 的纯追加时间线，没有顶部状态区。而它自我声明的用途（第 8 行）是"继续工作前先读取本文件"——该用途需要的是"现在到哪了"，不是"09-22 做了什么"。

建议在文件顶部加一个独立的"当前进行中 / 未提交 / 待验证"小节，历史条目保持在下。

### 3.4 两处表述问题（低优先级）

- **第 96 行的"403 粒子"**：这是 rc.2 条目的读数，但相同数值 `403` 在 rc.1 条目（第 85 行）出现过。两次独立采样给出同一精确值，疑为复制上一次读数。粒子上限为 420（第 57 行），403 未越界，但该数字的可信度需要打折扣。真正值得记的是同一条里的对象总量：240 敌人 + 22 弹体 + 52 特效 + 403 粒子 + 12 无人机 = 729。
- **"N 个测试文件"的计数口径**：从 rc.2 的"23 个"到 rc.4 的"24 个"是准确的文件数，但 `node --test` 报的是 `24 tests / 24 pass`——即平均每个文件只产出一个顶层测试。读者容易把"N 个测试文件通过"读成"N 个测试通过"，两者差一两个数量级。建议改述为"24 个测试文件、共 N 条断言"。

## 四、优先级

1. **统一版本查询参数**（问题 1）——唯一会直接造成线上故障的项。
2. **删除降级桩**（问题 2）——改动小，能立刻暴露所有隐式依赖。
3. **拆分 `game.js`**（问题 6 的前提）——按"模拟 / 渲染 / HUD"切，`draw*` 系列并入 `renderer.js`，`updateHud` 独立。这是唯一能止住继续膨胀的动作。
4. **worklog 加顶部状态区**（3.3）——恢复它自我声明的用途。

第 3 条之后，问题 3、5、6 都会自然解决。

## 五、值得保留的设计

- `cloud-sync.js` 把同步逻辑写成不依赖 DOM 的纯核心（`createStore({storage, defaults, uuid, changed})`），`cloud-ui.js` 只做界面，`cloud-config.js` 一行开关在 Pages 上关闭。分层干净。
- `test-harness.cjs` 从 `index.html` 正则抓 `id` 造假 DOM，强制测试环境跟随真实页面，杜绝"测试里有、页面上没有"。
- `combat-effects.js` 的 `weaponProfile` 同时供给模拟与检视面板，单一数据源，避免面板显示与实际伤害各算一套。
- worklog 的验证边界标注始终诚实（"不代表 Android/iOS 实机验证"、"该数据不应称为恒定 240 敌人"），这条纪律值得坚持。
